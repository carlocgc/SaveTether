# SaveTether phase 3.5: definitions from the Ludusavi manifest

Section 5a of the [implementation plan](implementation-plan.md) points here. This file holds the whole phase: why the manifest, the trial, the decisions, the conversion rules, the tasks (T1 to T9) and the exit test. A task's progress and "As built" notes are recorded in this file too, under the task. A delegated task needs only this file and the files it names.

Added 2026-11-19 by the owner. Goal: Add app and `app add` know most PC games that keep saves in a folder, without anyone checking each game by hand, and the emulators the manifest lacks have verified definitions of our own. Starts once phase 3's open items are done: "Add a folder by hand", the offer to move the programs to the per-user location, and phase 3's exit test.

**Why the manifest.** The [Ludusavi manifest](https://github.com/mtkennerly/ludusavi-manifest) is a YAML file of save locations, compiled from PCGamingWiki every 6 hours by a scheduled GitHub Actions workflow, MIT-licensed, and written so that other backup tools can use it (design 5.2, "Reusing the Ludusavi manifest"). Its paths are right for backing files up; SaveTether replaces a folder with a link, so the conversion decides which entries are safe to link, and the safety net (a backup before each operation, the comparison, Recover) bounds what a wrong path can do.

**Trial, 2026-11-19.** A throwaway converter (not in the repository) turned that day's manifest into SaveTether definitions and checked each with `DefinitionLoader`:

Of 18,679 save paths: 2,646 were globs, 2,048 single files, 1,083 macOS only and 2,019 folders that several games claim (a publisher folder or `My Games`), all left out. 2,339 sat below a per-account folder (`<storeUserId>`) and were kept by linking the folder above it.

Checked against games installed outside Steam on the owner's PC: the manifest's save folders existed for all six matched games that had saves. It also showed:
- Many games keep saves in a folder per store account, sometimes where the wiki does not say so (Final Fantasy XVI keeps `Steam/<account ID>` inside the folder the wiki gives). Linking the folder above the account folder takes in whatever account a device uses.
- The data has gaps: one game's save folder is tagged only as config, one game has no save paths, and one game's listed folders did not exist.
- The imported Cemu entry lacks the native Linux install that `definitions/cemu.jsonc` has, and calls Cemu a game: a verified definition must win over an imported one.
- Detection by a shared parent such as `{home}/Saved Games` finds every game on every PC; detection must check the game's own folder.

**Decisions, by the owner on 2026-11-19.**

| Decision | Choice |
|---|---|
| Games with platform cloud saves | In scope. The same game bought elsewhere has no cloud saves. A definition notes which stores' copies have cloud saves; nothing is refused (design 5.2) |
| How imported definitions reach the app | Converted in CI and built into the binary as one compressed file. A run-time download of a hash-pinned release can come later (design 5.9) |
| Which definition wins | Shared definitions, then verified built-in ones, then imported ones. An imported definition whose ID a verified one uses is dropped. Imported ones are labelled unverified wherever they are shown |
| Converter | A small C# tool in the repository, run in CI only, using YamlDotNet. Approved by the owner for the converter only; neither shipped program depends on it (design 5.2 records why YAML was dropped for definitions) |
| Licence | Ludusavi's MIT notice ships with the imported file, and PCGamingWiki is credited in the notices and in About. A note to Ludusavi's maintainer is a courtesy and does not block a release (design 5.2) |
| Found list | Ordered by the newest file inside each found save folder, most recent first, so a folder left behind by an old install sinks |

**Conversion rules,** from the trial:
- Only paths tagged `save`. A folder also tagged `config` is kept, with a quirk saying it may hold settings that should differ per device.
- Left out: globs, single files (until the single-file mappings stretch goal), macOS-only paths, placeholders SaveTether has no token for (`<root>`, `<winPublic>`, `<winProgramData>`, `<winDir>`), a folder claimed by more than one game, a token with nothing after it, and `My Games`, `Saved Games` or `Documents` on their own.
- A folder inside another kept folder of the same game is dropped; the outer link covers it.
- A path below `<storeUserId>` links the folder above it, with an entry depth that reaches past the account folder.
- Placeholders map to tokens: `<winAppData>` to `{appdata}`, `<winLocalAppData>` to `{localappdata}`, `<winLocalAppDataLow>` to `{locallow}`, `<winDocuments>` to `{documents}`, `<xdgData>` and `<xdgConfig>` to `{xdg_data}` and `{xdg_config}`, `<home>/.var/app/<id>` to `{flatpak:<id>}`, and `<base>` to `{install_dir}`.
- Installs: `windows` for Windows folders; `steam-proton` for the same folders as a winpath in the game's Proton prefix, when the manifest has a Steam app ID; `linux` and one `flatpak-<id>` per Flatpak; `install-dir` for saves inside the game's folder.
- Each install is detected by the game's own folder, never by a parent that every machine has.

**Tasks, 2026-11-20.** The table above, turned into tasks that can be handed out. Each task is one PR against `development`.

Two decisions were taken while planning:
- The owner chose how Add app's page 1 behaves. It lists the apps found on this device, newest save first, and then the ones already added. Every other definition shows only when the search matches it.
- The imported file is committed at `definitions/imported/ludusavi.jsonl.gz`, so builds are reproducible and work offline. The weekly workflow opens a pull request when the file changes.

The order: T1 comes first. T2, T3, T6 and T8 can then run side by side, since they touch different files. T4 follows T3, and T5 follows T4. T7 follows T2. T9 is last.

**Progress.**
- **T1 done, 2026-11-20** (branch `phase-3.5-t1-format`). `AppDefinition` gained `Tier`, `Origin`, `StoreIds`, `CloudSaves` and `TestedOn`, all optional with defaults, so existing callers are unchanged. A winpath's `prefix` is optional in the loader and the schema. `DefinitionLoader.ParseBundle(Stream)` returns the good definitions and the errors, each error as `bundle(<line>)`; a repeated ID is an error, blank lines are skipped, and text that is not gzip is one error.
- *As built:* the message from `PathResolver` for a missing prefix is unchanged. Core messages may not name command-line flags (`HintsTests` enforces it), so `--wine-prefix` is named by the CLI hint for `NeedsValue`, as before. The T1 line above said the message names the flag; that is done by the hint.

- **T2 done, 2026-11-20** (branch `phase-3.5-t2-converter`). `build/convert-ludusavi.cs` reads the manifest with YamlDotNet 16.3.0 and the core project, writes the bundle, and reads it back through `DefinitionLoader.ParseBundle`; one refusal fails the run. `--self-test` runs the 23 fixtures in `build/ludusavi-fixtures/` byte for byte, and a refused definition; CI runs it on linux-x64. `--self-test --bless` rewrites the expected files: read the diff before committing.
- *As built, where the rules left a choice:*
  - A path is a single file when its last part ends like a file name (`.` then a letter, up to 6 letters or digits). The manifest does not say. A folder starting with a dot under `<home>` is a Linux folder only. `<home>/Library` is macOS.
  - An install has one base, so a game with folders under two Windows tokens gets one install per token (`windows-appdata`, `windows-documents`; the same for `steam-proton` and `linux`). With one token the ID is plain (`windows`).
  - Roles are one per folder: `save`, `save-2`... for the Windows folders, shared by `windows` and `steam-proton` so the save is one copy on both. Native Linux folders are `linux-save`..., Flatpak folders `flatpak-save`..., install-dir folders `install-save`...: they are not paired with the Windows ones, since nothing says they hold the same files. Folders sort by path, so the order is stable.
  - An install's `detect` is its first folder. A Proton install is detected inside `{steam_compatdata:<id>}/pfx/drive_c/users/steamuser`. Windows games without a Steam ID get no Linux install yet (no way to detect inside a Wine prefix before T4).
  - A folder claimed by more than one game is judged by its manifest path, ignoring case, and not for `<base>` paths. The account depth is 1 plus the parts after `<storeUserId>`, at least 2, at most 8. A game with a Steam app ID is `slug-<steamid>`; those without one take the plain slug, numbered after the first. A game whose ID slug is a verified definition's ID is dropped.
  - `<winAppData>/../LocalLow/...` (and `../Local/`, `../Roaming/`, also from `<winLocalAppData>`) is rewritten to the sibling's own token. Without it the loader refused 6 games.
  - `Exclusions.Known` is empty: after that rewrite the loader accepts every definition.

Installs: 6,721 windows, 5,905 steam-proton, 1,064 linux, 6 flatpak, 2,372 install-dir. Paths left out: 2,378 globs, 2,250 single files, 1,596 macOS or DOS only, 1,282 unknown placeholders, 116 claimed by several games, 17 holding another game's folder, 24 nested, 92 with no placeholder. One game left out because a verified definition has its ID (Cemu).
- *Review of PR 71, as built:* the converter reads `when.store` as well as `when.os`. A folder the manifest gives only for other stores (GOG, Epic...) is not a `steam-proton` role path and does not detect the Proton install, which is detected by the first Steam or untagged folder. A folder that is an ancestor of another game's folder is dropped like a claimed one (the narrower folder stays with its own game). A nested folder passes its config and account marks, and an entry depth that reaches its entries, to the folder that covers it. A generated ID is checked against verified IDs and against every other game's plain slug. `<home>/AppData/{Roaming,Local,LocalLow}` and `<home>/Documents` map to their tokens (the AppData ones are not Linux folders). The gzip header names no OS (byte 9 is `0xff`), so Linux and Windows give the same bytes. *Second review round:* a path is a `steam-proton` role path only when one `when` entry allows both Windows and Steam (omitted fields allow anything), so `{windows, gog}` plus `{linux, steam}` gives a Windows role only (fixture `store-when-entries`). Nested folders are collapsed per install: a Steam folder inside a non-Steam Windows folder stays as a role of the `steam-proton` install alone, while the `windows` install keeps the parent (fixture `nested-folder`). The bundle was regenerated from the same manifest commit (`25a17c7`): the counts above are unchanged, only role paths differ. The Ludusavi MIT notice is at `definitions/imported/ludusavi.LICENSE.txt`.
- *Open, for later tasks:* **T4:** a definition's detect rule has one `dir`, so a game whose save folder differs by store (Skyrim SE: `My Games/Skyrim Special Edition` and `... GOG`) is detected by the first folder only; probing alternatives needs a format change. How linking behaves for a default role whose folder does not exist on a device is a T4/T5 question. **T7:** compare the decompressed JSONL, not the compressed bytes, to decide whether the bundle changed, since zlib versions can change the compressed output. **IDs (decided by the owner):** a game with a Steam app ID is always `slug-<steamid>`, so its ID is stable across manifest updates. Games without one are still numbered when their slugs clash, so those IDs can shift.
- *Differs from the trial:* more definitions, because `<base>` paths are not counted as claimed (each game has its own install folder, so two games with `<base>/saves` do not share one), which the trial's 2,019 claimed folders probably did; this is where the 2,372 install-dir installs come from. They only match once a device gives an install folder, which T4 and T5 handle.
